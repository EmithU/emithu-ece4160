Background

In previous labs, we designed and implemented a Kalman filter for predicting ToF data while incorporating knowedge of the car's physical characteristics. Kalman filters assume that noise is normally distributed; while this assumption can be reasonably made for ToF estimation, it cannot be made for ground localization due to the complexity of the task and multiple sources of noise present forming an unknown noise distribution.

This motivates a Bayes filter. Below is pseudocode representing the algorithm.

A Bayes filter is structurally similar to a Kalman filter; there is a prediction step (line 3) followed by an update step (line 4), where the prediction step tries to 'fill in the gaps' before new data is recieved. Like a Kalman filter, a Bayes filter returns a PDF representing a spread of possible values, and refines it as more and more data comes in. Unlike a Kalman filter (where we frequently disregard the variance altogether and just treat the mean as our 'nominal' value), the returned distribution is not necessarily normal.

The advantages of this are (primarily) twofold. Firstly, as mentioned before, noise does not need to be Gaussian for the Bayes filter to work effectively. Secondly, if values could be multimodal in nature (meaning that it's equally likely for a value to be one of n possibilities), a Bayes filter would properly encompass this, while a Kalman filter would not due to it's underlying assumptions about noise. The disadvantages are that the Bayes filter is more computationally expensive than a Kalman filter.

In the case of ground localization, we have no choice but to use a Bayes filter. It is a good idea to simulate the algorithm first, as this lets us isolate algorithmic challenges from implementation challenges.

Conclusions

Clearly, the Bayes filter (blue) does a far better job at predicting the ground truth location (green) than the plain odometry alone (red). We can see it failing when it has to trace a very large distance, which in the real world would go beyond what the ToF is able to read. This is most likely happening because our characterization of ToF noise does not take into account values when we are going beyond the specs of the ToF, and so the filter tries to extrapolate from this mischaracterization. This could possibly be fixed by detecting for very high ToF values and slightly modifying the behavior of the filter when this is detected.
