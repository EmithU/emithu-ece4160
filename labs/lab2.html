Lab 2

This lab seeks to set up and fully calibrate the provided ICM-20948 IMU.

Setup the IMU

Firstly, the IMU was plugged into the microcontroller. Thanks to the QUIIC connector, this was a very straightforward process.

With this done, the next step is establishing that it gives a data output at all, and that the data output changes predictably based on the force being applied to it.

The IMU communicates with the microcontroller through I2C. One feature of I2C is the ability for many devices to communicate on one I2C bus. To accomplish this, each device transmits an address along with it's data, and this address is unique between devices. For this IMU, that address is (mostly) hardcoded, with the exception of one bit. AD0_VAL is that bit, and it is set to 1 by default when the ADR jumper on the board is open. This allows us to potentially have 2 of this exact IMU model along the same I2C bus without data collisions.

IMUs typically contain an accelerometer, gyroscope, and sometimes a magnetometer, in one IC unit. Of particular relevance for this lab/course are the accelerometer and gyroscope. The accelerometer and gyroscope each have their own benefits and drawbacks; 'combining' their results through a complimentary filter allow us to have the 'best of both worlds', with precise and accurate data.

Pictured below is the code for plotting raw accelerometer data on the Arduino serial plotter, as well as a snapshot of the plot as the IMU was rotated smoothly. Accelerometers measure acceleration relative to a free-fall reference frame, meaning that when completely stationary and laying on one axis, that axis will report an acceleration of 1g; when not directly laying on one axis, each axis will report a component of gravity as their acceleration. By taking readings along each axis and performing trigonometry, we can figure out the absolute orientation of the IMU. While relatively accurate, they suffer from being sensitive to noise in the envronment out of the box, which is why all 3 axes show considerable 'imperfections' despite the IMU experiencing a relatively smooth motion. If noise wasn't present, all 3 of these lines would be significantly smoother.

Pictured below is a snapshot of a plot of raw gyroscope data as the IMU was rotated smoothly, in the same way as the accelerometer above. Gyroscopes measure angular velocities, and determining absolute orientations from a gyroscope involves adding to or subtracting these velocities from an accumulator variable. While being very precise for very small intervals of time and not being very sensitive to external noise, gyroscopes have an internal 'offset' and might still have small sources of constant noise. Because we are integrating gyroscope readings over time, even small imperfections in data accumulate very quickly.

As mentioned previously, raw accelerometer data tends to be very noisy. This noise can be systematically attenuated by transforming the signal to the frequency domain and removing high-frequency components. Random background noise and vibrational noise tends to exist at very high frequencies, and relevant data tends to be low frequency, so removing these high frequency components should remove a significant amount of noise.

If the robot never faces brief, external changes in orientation, any frequencies other than those close to or at 0Hz would be cut as we would know that only low-frequency components are relevant. We do not assume that the robot will never face brief changes in orientation; attenuating too much high-frequency data will reduce the 'responsiveness' of the robot. This is why we will incorporate gyroscope data later, but for now, it is best to optimize the accelerometer as much as possible by picking an optimal cutoff frequency.

Gyroscopes tend to accumulate error very quickly. Below is a plot of the reported roll, pitch, and yaw of the gyroscope as it is laying flat on a table, motionless (still at a dt of 1 millisecond). In just 4 seconds, all of roll, pitch, and yaw showed a consistent deviation from 0 degrees; over the course of a few minutes, this error will accumulate signficantly.

In my testing, adjusting the sampling frequency to be higher introduces exponentially more error, and lowering the sampling frequency is not realistic in the long-run because the robot will need to be doing many calculations beyond polling the gyroscope. However, we still want the highly accurate data that gyroscopes can provide in small time intervals. This motivates a complimentary filter, which fuses the data of the accelerometer and gyroscope into one set of values.

Sample Data

I wrote my code in a similar style to lab 1's faster method of collecting and sending data from the start. No delays were used, nor were any serial.prints during data collection.

My code is configured to run continuously until 1000 samples are collected. We can divide the sample count by the amount of time elapsed (4271 milliseconds) and multiply by 1000 to get a sample rate of 234.14 samples/second.

My code is configured to store Accel/Gyro/Comp data in separate arrays. This separation makes it far easier to understand what data is being accessed, versus indexing one array which can very easily result in hard-to-debug indexing errors. I have all of the arrays as double arrays because that is the data type outputted by the IMU and I want to avoid potential type mismatches or erasing potentially useful data.

The Artemis Nano has 384KB of memory. In theory, assuming that we are using doubles, we can store 384KB / 8B = 48000 samples total. This means we can store a max of 205 seconds of data. I have been using this method of storing and sending data throughout this lab, and my above plots end at just under 5 seconds with an array size of 1000. Clearly, 5 seconds of data is collection is possible using this method.
